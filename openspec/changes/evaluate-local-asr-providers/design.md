## Context

仓库目前只有 OpenSpec 规划，没有业务代码或既定 Python 工程。现有 `add-local-realtime-voice-service` 直接选择 FunASR 首实现，同时把 sherpa-onnx、faster-whisper 和 NVIDIA Parakeet/NIM 留作未来候选；这使统一 Provider 接口和系统结构可能在没有横向证据时被提前固化。参见 `proposal.md` 了解本变更动机，参见 `specs/asr-provider-evaluation/spec.md` 了解可观察的完成条件。

基准环境是 Windows 11 主机、Core Ultra 7 270K Plus、RTX 5060 Ti 16GB 和 32GB 内存。目标语音为中文、英文和中英混合；主实时链路需要验证 5 路延迟 SLA，10 路用于容量余量。各候选的安装方式、模型格式、流式语义、CUDA 依赖和许可条件并不相同，且部分候选可能只适合离线或句末二次校正。

## Goals / Non-Goals

**Goals:**

- 用相同输入、硬件、计时定义和结果格式得到可比较的候选证据。
- 先保留各候选原生语义，再从真实差异中提炼稳定的 Provider 能力模型。
- 让每一步都能独立运行、观察、解释和复盘，避免隐藏安装命令或只保留最终分数。
- 以能力硬门槛和角色化指标作出主实时、回退、二次校正和不采用决策。
- 把实验工具与后续产品 Gateway 解耦，同时生成足够明确的集成交接信息。

**Non-Goals:**

- 不在本变更中实现外部 WebSocket、数据库、录音、命令、设备、视觉或客户端模块。
- 不把所有 Runtime 强制塑造成相同的流式行为，也不为离线模型伪造 partial。
- 不训练、微调或量化模型；模型调参仅限官方或公开支持的推理配置。
- 不评测 OpenAI 或其他必须把音频发送到外部服务的云端 ASR。
- 不根据单一综合分数自动决定架构；最终角色必须能追溯到能力门槛和原始指标。

## Decisions

### 1. 采用“原生实验在前、统一抽象在后”的两遍结构

第一遍为每个候选建立最小原生实验，直接观察其加载、音频输入、会话状态、partial、final、VAD、热词、错误和释放行为。每个实验只引入运行该候选所需的最少结构，不依赖 Gateway 或预先完成的统一 Provider。

第二遍在全部候选完成或留下退出结论后，整理共同能力和差异，再定义统一 Provider 能力描述、事件和生命周期，并只为仍有目标角色的候选建立适配器。

先定义统一接口的替代方案会让第一个 FunASR 实现主导抽象，并可能把 faster-whisper 的分段推理或 NIM 的服务边界错误地塞进同一语义，因此不采用。完全不做统一适配的替代方案则无法验证后续 Gateway 的可替换边界，也不采用。

### 2. 实验台独立于产品服务并按职责分层

实施时建立以下逻辑边界，具体包名可遵循最终 Python 工程约定：

```text
ASR 实验入口
  ├─ 环境探测：硬件、驱动、Runtime、模型和依赖快照
  ├─ 语料目录：音频、参考文本、标签和版本清单
  ├─ 原生实验：每个候选自己的最小入口和依赖说明
  ├─ 统一适配：能力描述、会话生命周期和事件映射
  ├─ 回放与基准：离线输入、真实时间回放、并发和计时
  └─ 结果与报告：逐样本 JSONL、聚合 JSON、可读 Markdown
```

实验入口不得启动 FastAPI、PostgreSQL 或产品 Worker。这样能够先定位模型和 Runtime 问题，后续也能把实验工具作为 ASR Worker 的回归测试资产复用。

### 3. 每个候选使用隔离且可锁定的 Runtime

FunASR、sherpa-onnx、faster-whisper、Parakeet 和 NIM 不共享一个强行合并的依赖环境。每个候选保存自己的依赖锁定信息、模型准备说明和入口命令；GPU 路径优先在能够稳定访问 NVIDIA GPU 的 WSL2/Linux 或容器环境运行，纯 CPU 或原生 Windows 路径只有在确有评测价值时补充。

模型文件使用本地目录和内容或版本标识，实验结果引用标识而非依赖可变的“latest”。如果 NIM 镜像、凭据或许可不可获得，则在预检阶段形成退出记录；不把是否能够访问商业分发渠道当作代码失败。

使用单一共享虚拟环境的替代方案安装简单，但 CUDA、PyTorch、ONNX Runtime 和各项目版本容易互相污染，会损害可复现性，因此不采用。

### 4. 语料清单是比较的不可变输入契约

语料清单为每个样本保存稳定 `sample_id`、相对音频路径、内容摘要、采样率、声道、时长、场景标签、语言模式、参考文本和参考文本规范化版本。基线至少包含中文、英文、中英混合、静音、噪声、长句和短命令；音频统一保留原件，评测需要的 16kHz 单声道 PCM 输入由确定性预处理生成并记录来源。

修改音频、参考文本、标签或规范化规则都会产生新语料版本。报告以语料版本为比较边界，避免在样本变化后继续沿用旧分数。

### 5. 结果模型区分事实事件、派生指标和人工结论

逐样本原始结果保存输入和环境标识、候选配置、候选原始文字、规范化文字、事件时间、错误、退出状态和资源采样引用。流式候选额外保存带单调时钟的 partial、final、VAD endpoint 和取消事件；没有原生事件的候选将相应能力标为不支持，而不是生成空洞的模拟事件。

聚合层从原始结果计算 CER、WER、中英混合规范化错误、关键词命中、静音误识别、实时率、延迟分位数和资源峰值。报告层再解释适用角色和限制。三层分离使指标算法或文字结论变化时无需重跑无法复现的原始推理。

### 6. 延迟使用统一单调时钟和明确起止点

- 首个 partial 延迟从对应音频采集时间进入回放器开始，到候选产生第一个非空原生 partial 为止。
- final 延迟从 VAD endpoint 或显式段提交时刻开始，到稳定 final 可消费为止。
- ASR 排队时间从音频块进入有界基准队列开始，到候选开始消费为止。
- 推理耗时记录候选调用边界，实时率使用处理音频时长与推理墙钟时间计算。

所有计时使用同一进程或已校准进程中的单调时钟；墙钟仅用于报告产生时间。原生服务型 Runtime 如果跨进程，则同时记录客户端边界耗时和服务端可获取的内部耗时，不把两者混为一个指标。

### 7. 采用能力门槛加角色化比较，不使用一个总分掩盖差异

主实时候选的硬门槛是本地运行、目标语言覆盖、可持续会话、稳定 final、可接受的流式语义以及 5 路 SLA。只适合分段推理的候选仍可参加准确率和二次校正延迟比较，但不参加原生 partial SLA 排名。CPU 回退角色可以牺牲吞吐，但必须明确能够在无 GPU 条件下运行及其容量边界。

报告以能力矩阵和各指标原值为主，可提供便于阅读的分组排序，但不产生一个混合准确率、延迟、许可和部署难度的不透明总分。这样能够选择“主实时 + 二次校正 + 可选回退”的组合，而不是假设单一模型覆盖所有角色。

### 8. 并发测试必须逐级放大并包含资源释放门槛

每个有资格进入性能阶段的候选先完成模型加载、单文件推理、单路真实时间回放、取消和会话关闭检查。单路稳定后才运行 5 路，5 路结果完整后才运行 10 路。并发回放使用相同语料调度和真实时间节奏，预热轮次与正式轮次分开记录。

5 路用于主实时 SLA 验收；10 路用于观察崩溃、失败、积压、资源饱和和背压风险。每一级测试结束后检查活动会话、内存和显存是否回落到允许的稳定区间。直接从单样本跳到 10 路会让依赖、模型语义和并发问题混在一起，因此不采用。

### 9. 用可执行检查点承载学习过程

每个候选固定拆成预检、环境准备、最小加载、单样本、原生模式、统一语料、性能和总结检查点。每个检查点只引入一个主要概念，文档同时记录“为什么做、如何运行、期望看到什么、实际看到了什么、如何解释、下一步门槛”。

检查点完成状态由测试或结果文件支持，而不是只勾选任务。每次进入新候选前先复盘当前报告，确保失败同样转化为可学习结论。

### 10. 选型报告是后续语音服务的显式交接物

最终报告必须给出每个角色的选择或空缺、采用的模型与关键配置、能力映射、5 路和 10 路证据、已知限制、依赖锁定入口以及接入统一 Provider 时不得改变的语义。若没有候选通过主实时门槛，报告保持门槛失败并列出下一轮调整，不启动产品其他模块来掩盖 ASR 风险。

本变更不直接重写 `add-local-realtime-voice-service` 的工件。选型完成后使用独立的 OpenSpec 更新流程，把实际 Provider、模型、运行环境和角色组合回填到该变更，再开始其 apply 工作。

## Risks / Trade-offs

- [候选的模型、安装说明或许可在实施时已变化] → 每个候选先做能力与来源预检，锁定实际使用版本，并把不可获得视为有证据的退出结果。
- [不同候选支持的语言和流式语义不可直接比较] → 使用硬能力矩阵和角色化指标，缺失能力标为不支持，不用模拟值填补。
- [中英混合准确率受规范化规则显著影响] → 保存原始文字、规范化文字和规则版本，同时分别报告中文、英文和混合结果。
- [CUDA、PyTorch 和 ONNX 依赖互相污染] → 每个候选隔离 Runtime，公共回放器通过稳定的文件或进程边界调用候选入口。
- [模型下载占用大量网络时间和磁盘] → 在下载前记录模型标识、预计体积和缓存目录；同一文件复用本地缓存但校验标识。
- [NIM 或某些 NVIDIA 路径需要不可用的访问权限] → 把直接 Runtime 与 NIM 分开预检；不可访问路径留下退出报告，不阻塞其他候选。
- [实验步骤过细导致短期进度较慢] → 保持每步产物可复用为回归测试、安装文档和后续 Worker 验收，避免在产品集成阶段重复排障。
- [基准工具自身引入计时偏差] → 使用单调时钟、固定回放器、预热与正式轮次分离，并用合成无推理 Provider 校验计时开销。

## Migration Plan

1. 先加入只包含环境探测、语料清单校验和合成测试 Provider 的实验骨架，验证结果格式和计时工具本身。
2. 按 FunASR、sherpa-onnx、faster-whisper、Parakeet/NIM 顺序加入相互隔离的原生实验和报告，不修改现有语音服务工件。
3. 根据原生实验提炼统一 Provider 能力模型，为仍有角色价值的候选增加适配器并重跑相同语料。
4. 对有资格的候选逐级运行 1 路、5 路和 10 路测试，完成选型与集成交接报告。
5. 选型确认后，通过 OpenSpec 更新流程同步 `add-local-realtime-voice-service`，随后再进入该变更的实施。

实验工具尚未被产品依赖时，回滚只需停用对应候选入口并保留语料和历史报告。统一适配层被后续服务采用后，回滚应恢复上一份 Provider 配置和锁定版本；历史报告不得随 Runtime 回滚删除。
